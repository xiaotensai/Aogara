## 一、现状判断

程序功能上已是独立二开版本（多开、防顶号、占用优化、机器人释放等），
但**外表与元数据仍完全沿用上游 Aogara**。粗略统计源码中 `Aogara/aogara` 字样约 **689 处**
（含注释、日志前缀、localStorage 键、文件名、i18n 文案）。

必须分清两类改造：

| 类别 | 性质 | 处理 |
|---|---|---|
| **法律/署名** | 上游 Apache-2.0 要求保留署名与 NOTICE | 不能"抹掉"，只能"增加自己的声明" |
| **品牌/外观** | 窗口标题、Logo、产品名、图标、文案 | 可替换为自己的 |

**最重要的一条**：Apache-2.0 允许你改造成自己的产品、用自己的名字发布，
但**必须保留上游版权声明与 LICENSE/NOTICE**，并在显著位置说明"基于 Aogara 修改"。
"当成自己的产物" ≠ 抹掉上游署名——抹掉反而违法。下面的方案遵循这个边界。

## 三、P0 — 版本区分与法律合规（先做，零功能风险）

### 3.1 版本区分（已完成部分）

已改：

- `Cargo.toml` / `Cargo.lock`：`3.8.0 → 1.1.0`
- `frontend/src/lib/appVersion.ts`：`VERSION_FALLBACK = '1.1.0'`
- 编译验证：exe 内 `aogara/1.1.0`

保留未动：`frontend/src/announcements/entries.ts` 里的 `v3_8_0` 等公告历史条目——
那是上游发布历史记录，不是当前版本，改动反而会破坏公告排序逻辑。

### 3.2 加"衍生版"标识

在 UI 状态栏/关于页显示明确标识，例如：

```
YourName's Build 1.1.0 · 基于 Aogara (Apache-2.0) 修改 · 非官方版本
```

改动点：`frontend/src/components/Statusbar.tsx` 版本指示器附近，
`i18n/resources/*.json` 增加一条 `about.derivative` 文案（四种语言）。

### 3.3 法律合规（必须做，不能省）

现状：

- `LICENSE.txt` = Apache-2.0 原文（保留）
- `NOTICE` = `Aogara v3 / Copyright 2026 Shinkuan` + 第三方软件清单（保留）

做法：

1. **不要删除或改写** `LICENSE.txt` 和 `NOTICE`；
2. 在 `NOTICE` 顶部**追加**你的衍生声明：

```
Derived Build (YourName's Build) 1.1.0
Based on Aogara v3 — Copyright 2026 Shinkuan
Licensed under the Apache License, Version 2.0.
Changes: multi-session isolation, anti-top-out, low-load optimizations,
browser-close bot release, etc. (see docs/)
```

3. 若你对外发布二进制，README 首页写明"基于 Aogara 修改，非官方版本"；
4. 保留上游 README 里的第三方致谢表（`EndlessCheng/mahjong-helper`、
   `Xerxes-2/MajsoulMax-rs`、`smly/RiichiEnv` 等），避免二次遗漏署名。

> 注意：上游 `Cargo.toml` 依赖 `chromiumoxide`（git 依赖 shinkuan 的 fork）和
> `riichienv-core` 等，这些第三方许可义务随代码继承，不能因为改品牌而忽略。

## 四、P1 — 应用标识与视觉品牌

### 4.1 应用标识（核心三处）

| 文件 | 字段 | 当前值 | 建议 |
|---|---|---|---|
| `tauri.conf.json` | `productName` | `Aogara` | 你的产品名 |
| `tauri.conf.json` | `identifier` | `com.xiao.aogara` | `com.<yourname>.<app>` |
| `tauri.conf.json` | `windows[0].title` | `Aogara` | 你的产品名 |
| `Cargo.toml` | `package.name` | `aogara` | 可改成你的英文名（snake_case） |

**注意 identifier 一经发布就不要再改**——它决定 Windows 注册表、通知权限、
用户数据目录归属。改晚了等于变成另一个应用，旧配置不会迁移。

### 4.2 可执行文件名

当前部署：`<安装目录>\app\aogara.exe`。改名（如 `yourbuild.exe`）需同步：

- `tools/_pool-ipc.js` 等脚本里硬编码的进程名（若有）；
- `gpu-pref.ps1` 里 `GpuPreference` 注册表的目标进程路径（上一轮写入的是 `<安装目录>\app\aogara.exe`）；
- 快捷方式、开机自启、防火墙规则；
- 文档中所有 `aogara.exe` 引用。

建议：先只改 UI 层品牌，**可执行文件名最后改**（牵涉最多外部引用）。

### 4.3 视觉品牌

| 位置 | 当前 | 改法 |
|---|---|---|
| `frontend/src/components/BrandLogo.tsx` | `AogaraIcon` / `AogaraWordmark` 组件名 + 4 个 svg | 换成自己的 logo（保留 light/dark 双版本机制） |
| `frontend/src/assets/logo/aogara-*.svg` |  upstream logo | 自制或委托设计，替换文件 |
| `icons/*.png/ico/icns` | 上游图标全套 | 用你的 logo 重新生成全尺寸（Tauri 要求多尺寸） |
| `tauri.conf.json` `bundle.icon` | 指向上述 icons | 不变，只换文件内容 |

建议用 ImageGen 或设计工具生成一套极简标识，再用脚本批量出多尺寸图标
（保持文件名不变，最省事）。

### 4.4 文案（i18n）

四种语言资源 `frontend/src/i18n/resources/{en,ja,zh-CN,zh-TW}.json`：
其中 `AogaraMS` 是上游另一个产品的推广卡片文案。

两种做法：

- **保守**：只把 `AogaraMS` 推广卡片整块移除（避免给上游导流）；
- **彻底**：把产品名、关于页、错误提示里的 Aogara 字样全替换为你的名字。

推荐先做保守版——移除推广卡片，保留功能性文案，改动小、回归风险低。
相关组件：`frontend/src/components/sidebar/Sidebar.tsx`（promo card 逻辑）、
`frontend/src/lib/external.ts`（`AOGARAMS_GITHUB_URL` 等外链）。

## 五、P2 — 数据命名空间与更新器（有兼容代价，谨慎）

### 5.1 localStorage 键

前端有若干 `aogara.*` 命名空间的持久化键：

- `aogara.sidebar`（侧栏状态，`useSidebar.ts`）
- `aogara.delayScriptOffered`（延迟脚本提示，`DelayScriptUpdateDialog.tsx`）

改名会导致老用户的 UI 偏好重置。你是唯一用户，可以直接改；
若将来分发给别人，建议做一次迁移读取旧键。

### 5.2 日志 / 配置 / 数据目录

当前实际部署的数据都在 `<安装目录>\app\` 下：

- `configs/`、`logs/slot1..5/`、`profiles/p-*/`、`history/`、`ca/`

程序内部路径多为相对路径（`./logs/slot1` 等），改产品名后这些目录名**可以不动**——
它们只是文件夹，不暴露品牌。若想彻底，可在 `config.toml` 里统一改前缀，
但需同步 `logs/_aborted/` 归档脚本、文档、备份脚本里的路径。

**建议**：数据目录保持不变，避免把已经调好的五开配置搞乱。

### 5.3 更新器

`src/github/mod.rs` 的 `USER_AGENT = "aogara/<version>"` 会暴露品牌，
`src/updater/check.rs` 用 `CARGO_PKG_VERSION` 比对上游 release。

风险：版本改成 1.1.0 后，如果更新器被触发， upstream 的 3.8.0 会被判成"更新"，
可能提示你降级/升级到上游版本——**这是个真实隐患**。

处理方案（二选一）：

1. **彻底关闭更新检查**：移除/禁用 UI 的"检查更新"入口，不连上游 GitHub；
2. **指向自己的仓库**：把 repo 参数改为你自己的发布仓库（此时需自建 release 流程）。

推荐方案 1——个人产物不需要自动更新，手动替换 exe 更可控。

**已实施（2026-11-24 18:36，方案 1）**：`src/ipc/commands.rs` 的 `check_for_update`
直接 `Ok(None)`（= 已是最新），不再连 GitHub；`UPSTREAM_REPO` 常量保留并加 TODO 引子，
用户后续建好个人仓库后把该常量改为自己的 `owner/repo` 并删掉提前返回即可。
实测启动日志 github release 请求数 = 0，无更新红点。外链（`lib/external.ts` 4 项）
同轮置空 + `openExternal` 空值保护，留 TODO 引子，待用户填个人链接。

### 5.4 与"原生脚本"区分

你提到的"原生脚本"应指上游 Python 版 Aogara v2 / bridge.js 那套。
区分手段（低成本）：

- README/文档开头明确："本程序 = Rust/Tauri 独立构建 1.1.0，非 Python 脚本"；
- 版本号 1.1.0 自成体系，不与上游 3.x 对齐（已完成）；
- 在 `docs/` 增加"与原生脚本的差异"一节：无 Node 依赖、单 exe、
  五开会话隔离、防顶号、低占用等。

## 六、P3 — 发布形态

1. **快捷方式 / 开始菜单**：Tauri 打包会生成，产品名改了自然跟着变；
2. **开机自启**：若用 Windows 启动文件夹，快捷方式名和指向路径都要改；
3. **GPU 偏好**：上一轮 `gpu-pref.ps1` 写入的是 `<安装目录>\app\aogara.exe` 的高性能偏好，
   exe 改名后必须重跑 `-Apply`（先 `-Revert` 清旧的），否则新 exe 不走独显；
4. **防火墙**：Edge 调试端口 63503–63507 只监听 127.0.0.1，一般无需改规则；
5. **发布包**：若用 `workbuddy_sites_deploy` 或 GitHub Release，README/截图/i18n 都要一致。

1. **P0 法律合规**（保留 LICENSE/NOTICE + 追加衍生声明 + 状态栏标识）——零风险，先做；

4. **P2 更新器**（关掉上游检查）——防止版本误判，建议在 P1 后立刻做；
5. **P2 数据命名空间**（localStorage 键）——可选，改了要接受偏好重置；
6. **P3 发布形态**——exe 改名 + GPU 偏好 + 快捷方式，最后做。

每一步前备份 `Cargo.toml`、`tauri.conf.json`、前端源码与当前 exe（沿用 `aogara.pre-*` 命名）。
回滚：恢复文件 → 重新构建 → 部署备份 exe。
